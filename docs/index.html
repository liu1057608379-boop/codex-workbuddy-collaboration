06 / TROUBLESHOOT
遇到问题，从这里找答案。

 
复制 skill 后，为什么仍然无法派工？
Skill 是给 Codex 的协作指令，不是桥接服务。你还需要可信、兼容的完整 WorkBuddy Gateway 和已注册的 MCP。确认工具已加载、WorkBuddy 已登录，并按完整项目的安装文档核连接。本仓库没有 Gateway 源码或安装器。

 
为什么每一轮还要确认模型？
确认只覆盖准确项目、会话和本轮任务。新派工、外部返工或换会话会创建新的确认范围。历史记录和界面默认值不能证明本次实际调用模型；同一已确认范围则不需要反复询问。空会话可先发非业务就绪消息核实际模型。

 
任务一直 queued 或 working，应该重新提交吗？
不要。queued 只是受理，working 只是领取记录。先用原 taskId 有界等待，检查一次实际登录、会话绑定、服务或错误；领取后还要核正文和实际工具活动。期限届满报告阻塞，回执不确定时保留原身份核查，不能换编号重复派工。

 
WorkBuddy 说完成了，为什么还要验收？
回报完成代表执行轮次结束，不证明业务正确。Codex 应检查真实路径、关键内容、相关 diff 与必要测试，并核 task/attempt/session 和 runtimeSource。accept 接口只记录检查结论，本身不会替你运行检查。选择用户自行验收时保留待验收状态。

 
工具提示权限不足，是否需要全部放开？
不需要。先核具体命令、资源与实际拒绝原因，以脱敏结论交用户处理必要权限。不要导出凭据或权限全集，不自动改安全规则，也不以替代路径绕过拒绝。SQLite 侧车访问错误也不意味着要重建原生数据库。

 
网页里的“复制”和检查项会上传我的信息吗？
不会。本页没有外部脚本、统计或网络请求；只有点击 GitHub 与文档链接时会导航。任务表单不持久化，只有四个自查勾选值保存在浏览器本地，且不包含任务内容。浏览器不允许直接写剪贴板时会显示手动复制框。

 
这些步骤是否保证所有 WorkBuddy 版本都可用？
不保证。本公开包不把个人环境历史验证当成新机器通过。Gateway 接口、桌面前台消息投影和模型持久化可能随版本变化，需要实际验证。随包脚本测试只验证保护逻辑，不证明真实桌面端到端协作或重启恢复可用。

 
如何打开指南，能直接在 GitHub 上阅读吗？
GitHub 仓库中的 HTML 文件页展示源码。下载仓库后双击 docs/index.html 即可离线使用，不需要安装网页依赖。也可由仓库管理员另行配置 GitHub Pages，选择 main 分支的 /docs 目录；本指南不代表该站点已启用。
